Bab 4.2

Referensi dan Borrowing

Masalah dengan kode tuple di subbab sebelumnya adalah kita harus mengembalikan String ke fungsi pemanggil supaya kita masih bisa memakai String itu setelah pemanggilan calculate_length, karena String-nya di-move ke calculate_length. Sebagai gantinya, kita bisa menyediakan sebuah referensi ke nilai String itu. Referensi mirip pointer, dalam artian ia adalah sebuah alamat yang bisa kita ikuti untuk mengakses data yang disimpan di alamat itu; data itu dimiliki oleh variabel lain. Berbeda dari pointer, sebuah referensi dijamin selalu menunjuk ke nilai valid bertipe tertentu selama masa hidup referensi itu.

Berikut cara mendefinisikan dan memakai fungsi calculate_length yang menerima referensi ke sebuah objek sebagai parameter, alih-alih mengambil ownership nilainya:

Nama berkas: src/main.rs

fn main() {
    let s1 = String::from("hello");

    let len = calculate_length(&s1);

    println!("Panjang dari '{s1}' adalah {len}.");
}

fn calculate_length(s: &String) -> usize {
    s.len()
}

Pertama, perhatikan semua kode tuple di deklarasi variabel dan nilai kembalian fungsinya sudah hilang. Kedua, perhatikan kita mengoper &s1 ke calculate_length, dan di definisinya, kita menerima &String alih-alih String. Tanda ampersand ini merepresentasikan referensi, dan mereka memungkinkanmu merujuk ke sebuah nilai tanpa mengambil ownership-nya.

ℹ️ Dereferencing

Kebalikan dari mereferensikan lewat & adalah dereferencing, dilakukan dengan operator dereference, *. Kita akan lihat beberapa pemakaian operator dereference di Bab 8 dan membahas detailnya di Bab 15.

Mari lihat lebih dekat pemanggilan fungsi ini:

let s1 = String::from("hello");

let len = calculate_length(&s1);

Sintaks &s1 memungkinkan kita membuat sebuah referensi yang merujuk ke nilai s1 tapi tidak memilikinya. Karena referensi itu tidak memilikinya, nilai yang ditunjuknya tidak akan di-drop ketika referensinya berhenti dipakai.

Begitu juga, signature fungsinya memakai & untuk menandakan bahwa tipe parameter s adalah sebuah referensi. Mari tambahkan beberapa anotasi penjelas: 

fn calculate_length(s: &String) -> usize { // s adalah referensi ke sebuah String
    s.len()
} // Di sini, s keluar dari scope. Tapi karena s tidak memiliki apa yang
  // ditunjuknya, String-nya tidak di-drop.

Scope tempat variabel s valid sama seperti scope parameter fungsi mana pun, tapi nilai yang ditunjuk referensinya tidak di-drop ketika s berhenti dipakai, karena s tidak punya ownership. Ketika fungsi punya referensi sebagai parameter alih-alih nilai sesungguhnya, kita tidak perlu mengembalikan nilainya untuk mengembalikan ownership, karena kita memang tidak pernah punya ownership-nya.

Kita menyebut aksi membuat sebuah referensi sebagai borrowing (meminjam). Seperti dalam kehidupan nyata, kalau seseorang memiliki sesuatu, kamu bisa meminjamnya dari mereka. Ketika selesai, kamu harus mengembalikannya. Kamu tidak memilikinya.

Jadi, apa yang terjadi kalau kita coba mengubah sesuatu yang sedang kita pinjam? Coba kode berikut. Spoiler: tidak akan bekerja!

❌ Belum bisa dikompilasi

Nama berkas: src/main.rs

fn main() {
    let s = String::from("hello");

    change(&s);
}

fn change(some_string: &String) {
    some_string.push_str(", world");
}

Sama seperti variabel yang immutable secara default, begitu juga referensi. Kita tidak diizinkan mengubah sesuatu yang kita punya referensinya (kecuali referensinya mutable).

Mutable Reference

Kita bisa memperbaiki kode sebelumnya supaya mengizinkan kita mengubah nilai yang dipinjam, dengan sedikit perubahan yang memakai mutable reference:

Nama berkas: src/main.rs

fn main() {
    let mut s = String::from("hello");

    change(&mut s);
}

fn change(some_string: &mut String) {
    some_string.push_str(", world");
}

Pertama, kita ubah s menjadi mut. Lalu, kita buat mutable reference dengan &mut s saat memanggil fungsi change, dan update signature fungsinya menerima mutable reference dengan some_string: &mut String. Ini membuat sangat jelas bahwa fungsi change akan mengubah nilai yang dipinjamnya.

Mutable reference punya satu pembatasan besar: kalau kamu punya mutable reference ke sebuah nilai, kamu tidak boleh punya referensi lain ke nilai itu. Kode berikut yang mencoba membuat dua mutable reference ke s akan gagal:

❌ Belum bisa dikompilasi

Nama berkas: src/main.rs

let mut s = String::from("hello");

let r1 = &mut s;
let r2 = &mut s;

println!("{r1}, {r2}");

Berikut errornya:

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0499]: cannot borrow `s` as mutable more than once at a time
 --> src/main.rs:5:14
  |
4 |     let r1 = &mut s;
  |              ------ first mutable borrow occurs here
5 |     let r2 = &mut s;
  |              ^^^^^^ second mutable borrow occurs here
6 |
7 |     println!("{r1}, {r2}");
  |                -- first borrow later used here

For more information about this error, try `rustc --explain E0499`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

Error ini bilang kode ini tidak valid karena kita tidak bisa meminjam s sebagai mutable lebih dari sekali dalam satu waktu. Mutable borrow pertama ada di r1 dan harus bertahan sampai ia dipakai di println!, tapi di antara pembuatan mutable reference itu dan pemakaiannya, kita mencoba membuat mutable reference lain di r2 yang meminjam data yang sama dengan r1.

Pembatasan yang mencegah banyak mutable reference ke data yang sama dalam satu waktu mengizinkan mutasi, tapi dengan cara yang sangat terkontrol. Ini sesuatu yang sering membuat Rustacean baru kesulitan, karena kebanyakan bahasa mengizinkanmu mengubah kapan pun kamu mau. Keuntungan dari pembatasan ini: Rust bisa mencegah data race saat compile-time. Sebuah data race mirip dengan race condition dan terjadi ketika tiga perilaku ini muncul:

  • Dua atau lebih pointer mengakses data yang sama pada saat bersamaan.
  • Setidaknya satu dari pointer itu dipakai untuk menulis ke data itu.
  • Tidak ada mekanisme yang dipakai untuk menyinkronkan akses ke data itu.

Data race menyebabkan undefined behavior dan bisa sulit didiagnosis serta diperbaiki ketika kamu mencoba melacaknya saat runtime; Rust mencegah masalah ini dengan menolak mengompilasi kode yang mengandung data race!

Seperti biasa, kita bisa memakai kurung kurawal untuk membuat scope baru, yang memungkinkan banyak mutable reference — hanya saja tidak bersamaan: 

let mut s = String::from("hello");

{
    let r1 = &mut s;
} // r1 keluar dari scope di sini, jadi kita bisa membuat referensi baru tanpa masalah.

let r2 = &mut s;

Rust menerapkan aturan serupa untuk menggabungkan mutable dan immutable reference. Kode berikut menghasilkan error:

❌ Belum bisa dikompilasi
let mut s = String::from("hello");

let r1 = &s; // tidak masalah
let r2 = &s; // tidak masalah
let r3 = &mut s; // MASALAH BESAR

println!("{r1}, {r2}, and {r3}");

Berikut errornya:

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:14
  |
4 |     let r1 = &s; // no problem
  |              -- immutable borrow occurs here
5 |     let r2 = &s; // no problem
6 |     let r3 = &mut s; // BIG PROBLEM
  |              ^^^^^^ mutable borrow occurs here
7 |
8 |     println!("{r1}, {r2}, and {r3}");
  |                -- immutable borrow later used here

For more information about this error, try `rustc --explain E0502`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

Fiuh! Kita juga tidak bisa punya mutable reference selagi kita punya immutable reference ke nilai yang sama.

Pengguna sebuah immutable reference tidak berharap nilainya tiba-tiba berubah begitu saja! Tapi, banyak immutable reference diizinkan karena tidak ada satu pun yang sekadar membaca data itu bisa memengaruhi pembacaan orang lain terhadap data yang sama.

Ingat, scope sebuah referensi dimulai dari titik ia diperkenalkan dan berlanjut sampai terakhir kali referensi itu dipakai. Misalnya, kode berikut akan berhasil dikompilasi karena pemakaian terakhir immutable reference-nya ada di println!, sebelum mutable reference-nya diperkenalkan: 

let mut s = String::from("hello");

let r1 = &s; // tidak masalah
let r2 = &s; // tidak masalah
println!("{r1} and {r2}");
// Variabel r1 dan r2 tidak akan dipakai lagi setelah titik ini.

let r3 = &mut s; // tidak masalah
println!("{r3}");

Scope immutable reference r1 dan r2 berakhir setelah println! tempat mereka terakhir dipakai, yaitu sebelum mutable reference r3 dibuat. Scope-scope ini tidak tumpang tindih, jadi kode ini diizinkan: compiler bisa tahu bahwa referensinya sudah tidak dipakai lagi di titik sebelum akhir scope-nya.

Walaupun error borrowing kadang menjengkelkan, ingat bahwa itu compiler Rust menunjukkan potensi bug lebih awal (saat compile-time, bukan runtime) dan menunjukkan persis di mana masalahnya. Jadi, kamu tidak perlu melacak kenapa datamu bukan seperti yang kamu kira.

Kenapa Rust melarang mutable reference dan immutable reference aktif secara bersamaan ke data yang sama?

Dangling Reference

Di bahasa dengan pointer, sangat mudah keliru membuat dangling pointer — pointer yang merujuk ke lokasi memori yang mungkin sudah diberikan ke pihak lain — dengan membebaskan sebagian memori sambil tetap menyimpan pointer ke memori itu. Di Rust, sebaliknya, compiler menjamin referensi tidak akan pernah menjadi dangling reference: kalau kamu punya referensi ke suatu data, compiler akan memastikan data itu tidak akan keluar dari scope sebelum referensinya keluar dari scope.

Mari coba membuat dangling reference untuk melihat bagaimana Rust mencegahnya dengan error compile-time:

❌ Belum bisa dikompilasi

Nama berkas: src/main.rs

fn main() {
    let reference_to_nothing = dangle();
}

fn dangle() -> &String {
    let s = String::from("hello");

    &s
}

Berikut errornya:

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0106]: missing lifetime specifier
 --> src/main.rs:5:16
  |
5 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: consider using the `'static` lifetime, but this is uncommon unless you're returning a borrowed value from a `const` or a `static`
  |
5 | fn dangle() -> &'static String {
  |                 +++++++
help: instead, you are more likely to want to return an owned value
  |
5 - fn dangle() -> &String {
5 + fn dangle() -> String {
  |

For more information about this error, try `rustc --explain E0106`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

Pesan error ini merujuk ke fitur yang belum kita bahas: lifetime. Kita akan bahas lifetime detail di Bab 10. Tapi, kalau kamu abaikan bagian tentang lifetime-nya, pesan ini sebenarnya sudah berisi kunci kenapa kode ini bermasalah: 

this function's return type contains a borrowed value, but there is no value
for it to be borrowed from

Mari lihat lebih dekat apa yang sebenarnya terjadi di setiap tahap kode dangle kita:

❌ Belum bisa dikompilasi

Nama berkas: src/main.rs

fn dangle() -> &String { // dangle mengembalikan sebuah referensi ke String

    let s = String::from("hello"); // s adalah String baru

    &s // kita mengembalikan sebuah referensi ke String, s
} // Di sini, s keluar dari scope dan di-drop, jadi memorinya hilang.
  // Bahaya!

Karena s dibuat di dalam dangle, ketika kode dangle selesai, s akan didealokasikan. Tapi kita mencoba mengembalikan referensi ke situ. Itu berarti referensi ini akan menunjuk ke String yang tidak valid. Itu tidak baik! Rust tidak akan mengizinkan kita melakukan ini.

Solusinya di sini adalah mengembalikan String secara langsung:

fn no_dangle() -> String {
    let s = String::from("hello");

    s
}

Ini bekerja tanpa masalah apa pun. Ownership-nya dipindahkan ke luar, dan tidak ada yang didealokasikan.

Aturan Referensi

Mari kita rekap apa yang sudah kita bahas tentang referensi:

  • Dalam satu waktu, kamu bisa punya salah satu dari: satu mutable reference, atau sejumlah berapa pun immutable reference.
  • Referensi harus selalu valid.

Selanjutnya, kita akan lihat jenis referensi lain: slice.

Ringkasan

  • Referensi (&) memungkinkan sebuah fungsi memakai nilai tanpa mengambil ownership-nya — disebut borrowing.
  • Referensi immutable secara default; pakai &mut untuk membuatnya bisa mengubah nilai yang dipinjam.
  • Aturan borrowing: boleh punya banyak immutable reference SEKALIGUS, ATAU tepat satu mutable reference — tidak pernah keduanya bersamaan. Ini mencegah data race di compile-time.
  • Scope sebuah referensi berakhir di titik terakhir kali ia dipakai (Non-Lexical Lifetimes), bukan selalu di akhir blok kode.
  • Compiler mencegah dangling reference: sebuah referensi tidak akan pernah bisa hidup lebih lama dari data yang ditunjuknya.
